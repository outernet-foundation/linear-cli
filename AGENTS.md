# linear-cli

## What this is

`linear-cli` is the audited write path into Linear: a small typer CLI (`uv run linear`) that talks directly to Linear's GraphQL API over `httpx`, generating each query or mutation from a template at call time. It exists so that every ticket or project write — from an agent or a human — is transparent, reviewable, and on-convention, rather than an ad-hoc `curl` or an opaque MCP server. Beyond the tool, this doc is the home for **the universal conventions every ticket follows** — the rules the tool enforces via `validation.py`, applicable to any workspace the tool is pointed at. Workspace-specific facts (team keys) are deterministic data living in `~/.config/linear-cli/config.json`, not prose here; label taxonomy is introspectable live via `label list`.

The package is `linear_cli` (src-layout under `src/linear_cli/`); consumer repos git-reference it and re-expose the `linear` console script through their own `[project.scripts]`, or install it globally via `uv tool install`.

## Shape

### The tool

- `cli.py` — the typer app (noun-verb sub-apps: `issue`, `project`, `team`, `workflow-state`, `label`, `user`, `relation`, `comment`). The GraphQL transport (`graphql()`, `mutate()`, `paginate()`) and query generation (`build_mutation()`, `build_list_query()`) live in `api.py`. Three top-level commands: `lint` reads every non-completed team issue (`--include-canceled` extends the scan) and emits one row per body or title that violates a convention (missing canonical section header, non-absolute link, bare filename hostname, bare repo-relative path, forbidden implementation-plan section, ordinal/label title prefix); `--require-label-parent <group>` adds a per-ticket label-presence check; `--fix-paths` auto-resolves bare paths to full GitHub blob URLs (discovers repo URLs by scanning sibling directories of CWD for git remotes on `main`, writes fixes immediately — run without the flag first to audit); `--design-orphans` flags design docs no open ticket links; exits non-zero if any violations found. `find-references` scans git-tracked markdown/yaml/json for a ticket identifier (`GOV-29`) and emits `{source, line, context}` rows; `--scan-linear` also searches Linear ticket bodies. Per-noun verbs: `issue list` paginates a team's issues so a caller can dedup before writing (each row carries its `project` name, or null when loose, plus `created_at` for age triage; `--include-archived` surfaces archived issues with `archived_at`; no team = workspace-wide), `issue get` fetches one issue's full body by id or identifier, `issue create`/`issue update` are the write gate — stdin body, convention validation, `--add-label`/`--remove-label` for incremental label changes (PATCH) vs `--label` for wholesale replace (PUT), `--team KEY` alone re-homes the issue (cross-team move when key differs), `--state NAME --team KEY` resolves the named state against that team's workflow and closes the issue; `--priority 0|1|2` sets none/urgent/high; `--assignee <email|name|id>` resolves a workspace user (`user list` discovers ids; `--unassign` clears); `--title` rewrites the title; `--id` accepts identifiers like `GOV-21` so callers never need UUIDs, `issue unarchive` restores an archived issue, `issue snapshot` freezes selected issues (`--issue` repeatable, or `--label`) as indented JSON carrying full detail so a caller can capture Linear state into git, `relation list` emits one `{source, target, type}` row per outgoing relation (each `blocks` edge exactly once, read off the blocker's `relations` connection — the mirror `inverseRelations` on the blocked issue is not walked), `relation create` writes a `blocks` edge, `comment create`/`comment delete` (comments cannot be edited in place — fixing one means deleting and reposting), `project list`/`project create`/`project update`/`project delete`, `team list`/`team create`/`team update`, `workflow-state list`/`workflow-state create`/`workflow-state archive` (archive is the only retirement path — Linear exposes no hard delete for workflow states), `label list`/`label ensure`/`label update`/`label delete`, `user list` emits one row per workspace user (id, name, email, active) so `--assignee` targets resolve, `snapshot` captures all teams, workflow states, projects, labels, and every issue (including archived) as a single indented JSON document for a complete restore point. `--team` is required on team-scoped create verbs (`issue create`, `project create`, `workflow-state create`) and on `workflow-state list`; optional on filter verbs (`issue list`, `relation list`, `lint`; omitting means workspace-wide); conditional on `issue update` and `project update` (gates `--state`, performs cross-team moves, sets project team set). Rich markdown bodies arrive on **stdin**; results are emitted as JSON on **stdout** so a caller can thread them into later calls.
- `api.py` — GraphQL transport and query generation. `graphql()` sends a single generated query string over `httpx` and returns `dict[str, object]`; `mutate()` wraps the mutation, validates success, and returns the response node dict. `build_mutation()` and `build_list_query()` generate every query and mutation string at runtime from a `Resource` dataclass (node name + return-field selection) per noun — Linear's regular `<noun><Verb>` naming (`teamCreate`, `issueUpdate`, `projectDelete`) means no static `.graphql` file. Adding a new resource type is one `Resource(...)` entry in `RESOURCES` plus CLI command functions; no new GraphQL operations or pydantic models. Credentials resolve via `~/.config/linear-cli/config.json` profiles (with a `--profile` global override and per-cwd `path_defaults` longest-prefix resolution); the tool errors if no config exists.
- `models.py` — five generic pydantic types shared across nouns: `LinearModel` (base with `populate_by_name`), `PageInfo`, `Connection[NodeT]`, `NodeList[NodeT]`, and `ResponsePayload` (validates the raw HTTP response at the `graphql()` boundary). Node models (`IssueListNode`, `LabelNode`, etc.) and their `*Data` wrappers live with their noun files, not here. Mutation payloads are not modeled — `mutate()` validates success and returns the node as `dict[str, object]`.
- `nouns/` — one file per noun, each owning its node models, `*Data` wrappers, GraphQL field constants, and resolution helpers (`resolve_team_id` in `team.py`, `resolve_label_ids` in `label.py`, `resolve_user_id` in `user.py`, `snapshot_issue_dict`/`identifier_sort_key` in `issue.py`). Cross-noun imports are acyclic: `team` and `user` are leaves (import no sibling); `label` and `workflow_state` depend on `team`; `issue` depends on `team`, `user`, `label`, and `workflow_state`; `project` depends on `team`. `user` is read-only (a `user list` query plus the `resolve_user_id` resolver backing `--assignee`), so it has no `RESOURCES` entry — assignment is written through the `issue` mutation's `assigneeId`.
- `profiles.py` — pydantic models and resolver for `~/.config/linear-cli/config.json`. Holds the schema (`Profile` carrying `api_key` plus the `paths` list of filesystem prefixes that route to this workspace; `ProfileConfig` as a `RootModel[dict[str, Profile]]` so the JSON file is a bare map at the top level, not wrapped in a `profiles` key) and the longest-prefix resolver that flattens `profiles[*].paths` into a single path → profile-name map and picks a profile from CWD. No `default_profile` — resolution errors loudly rather than silently falling back, since a wrong-workspace write on a write path is the exact bug silent defaults produce. Team is not in the config at all; see the Profiles section for why.
- `validation.py` — the title/body convention checks, shared by the `issue create`/`issue update` write gate and the `lint` audit so the two can never disagree.

### Profiles

Workspace credentials and per-repo routing live in `~/.config/linear-cli/config.json`, not in this doc and not committed to any repo. The file IS a map of profile-name → profile, where each **profile** is a workspace: it carries the API key (which is workspace-scoped in Linear) and the list of filesystem paths whose default workspace this is. **Team is never in the config** — every team-scoped verb takes `--team` explicitly, because picking a team means picking a ticket lifecycle (Linear's workflow states are team-scoped), and a single repo produces tickets in multiple lifecycles (a governance resolution and a build-script bug both get filed from `/workspace/governance`, but they belong to different teams). Forcing `--team` on every team-scoped call surfaces that decision rather than hiding it behind a misleading default. Shape:

```json
{
  "foundation": {
    "api_key": "...",
    "paths": ["/workspace/placeframe", "/workspace/governance", "/workspace/linear-cli"]
  },
  "personal": {
    "api_key": "...",
    "paths": ["/workspace/pulsar"]
  }
}
```

Profile resolution order: `--profile <name>` flag (if given) → longest-prefix match on the flattened union of every profile's `paths` against the resolved CWD → hard error. No silent default. The resolver flattens `profiles[*].paths` into a single path → profile-name map on load, then runs longest-prefix on it; if two profiles claim the same path, the later one in JSON order wins. **Team is always a per-call flag** — `--team KEY` on every team-scoped verb, required on verbs where team is structurally needed (`issue create`, `project create`, `workflow-state create`, `workflow-state list`), optional on verbs where team is a filter (`issue list`, `relation list`, `lint`; omitting means workspace-wide), and conditional on verbs where team gates another flag (`issue update --state` requires `--team`; `issue update --team` performs a cross-team move; `project update --team` sets the project's team set, repeatable for multi-team spanning). Label taxonomy is not mirrored in config — `label list` is authoritative and always current. Each profile is a distinct Linear workspace with its own teams — a team in one workspace is not visible in another. Before filing a ticket in a repo, run `linear team list` from that repo's directory to discover which teams exist in the resolved workspace. Never assume a team's existence from another workspace.

### Projects

**Projects** exist only for real multi-issue initiatives. A project's direct issues are its phases/workstreams; sequence between them is modeled with `blocks` relations, and each phase explodes into ~1:1-with-PR sub-issues when it is picked up.

A ticket's **team** picks its lifecycle — Linear workflow states are team-scoped, so PLE carries the engineering lifecycle (Backlog → Todo → In Progress → In Review → Done) and GOV carries the board-action lifecycle (Backlog → Ready → Done). A ticket's **project** picks its scope — a project groups related work, can span multiple teams, and is the unit of "this is governance work" / "this is the Q3 launch." The two are orthogonal: an engineering chore for the ECEF geo-anchoring layer is team=PLE, project=ECEF geo-anchoring layer. Decide team first ("what status workflow does this follow?"), then project ("what scope does this belong to?").

A project's `teamIds` list gates which teams' issues it can collect. `issue update --project X` on an issue whose team isn't in project X's `teamIds` fails with "Discrepancy between issue team and state, cycle or project" — the fix is `project update --id X --team <existing> --team <new>` (repeatable) to extend the team set, not `issue update --team` to move the ticket.

## Constraints

**Direct GraphQL, not MCP and not hand-rolled `curl`.** The workspace is written to rarely and by few actors, so MCP's managed-OAuth convenience does not pay for its opacity; a direct client is portable to every context (agent, CI, by hand) and every mutation is one auditable HTTP call. Every write goes through a tool verb — do not hand-write mutations or add an MCP. When a new kind of write is needed, add a verb and a `Resource` entry in `RESOURCES` (`api.py`).

**Extend the tool, do not wrap it.** If you need a capability the CLI lacks — a new filter, an aggregation, a bulk operation — add a verb. Do not pipe CLI output through inline Python (`python3 << 'EOF'`, `python3 -c`) to compensate for a missing feature; inline wrapping produces code that vanishes when the terminal scrolls, while a verb is durable, auditable, and available to every caller. The verb pattern is one typer command function under the appropriate noun sub-app; mutations delegate to the generic `mutate()` and queries to `graphql()` with a template-built string from `api.py`.

**`py.typed` must ship in the wheel.** `[tool.hatch.build.targets.wheel] include` lists `src/linear_cli/py.typed`; drop it and downstream type checkers lose the package's type information. The CI wheel-build is the guard.

**Tickets are declarative and durable, not plan files.** A ticket states an *outcome that is not yet true*, not a sequence of steps to reach it. This is the root convention; the rest follow from it.

- **No implementation plans in a ticket** — no file lists, no step sequences. Which files are relevant goes stale between authoring and pickup, and discovering the current surface is the first act of implementation. The implementer captures it as just-in-time sub-issues or in the PR, not the author up front.
- **The done-condition is a verifiable invariant, not a task checklist.** "Zero `NDArray` imports outside generated code" survives a year and a grep confirms it; "migrate the thirteen files" rots the moment the tree moves.
- **Descriptions are status-free.** The `**Why:**` section describes the gap or situation the ticket addresses — not the current state of artifacts. Progress lives in the issue's state, sub-issue completion, comments, and the project bar — never baked into description prose ("already done: X", "currently only Y is filed", "unsent"). Status in prose is wrong the moment it is written.
- **Design depth lives in the co-located `AGENTS.md`; the ticket links to it.** Ticket ≠ doc. Mechanism and rationale that outlive the ticket belong in that doc, not inlined into the ticket body.

**Titles are imperative, verb-first, and outcome-oriented.** A noun-phrase title ("Multi-state charitable registration") is wrong — rewrite it verb-first ("Register for charitable solicitation in NY, CA, and MO"). No ordinal prefixes — sequence is the `blocks` graph's job, and a prefix is a second, dumber copy that goes stale on reorder. No `repo`/`type` prefixes — labels carry those. Titles are the primary index and generate branch slugs, so they stay short and jargon-free.

**Body template: three parts, one canonical dialect.** The section headers are exactly `**Why:**`, `**Done when:**`, and `**Links:**` — bold, trailing colon, that spelling — and each section's text begins on the *same line* as its header (`**Why:** <text>`, not the header alone on its own line), so bodies can't drift into the `**Why.**` / `**Why**` / `### Why` or header-then-blank-line variants a hand-authored board accumulates. `**Why:**` is one to three self-contained sentences (a cold reader with no other docs open still understands the ticket); `**Done when:**` is the invariant; `**Links:**` is the spec, project, and related issues. The same-line rule is enforced for `Why` and `Done when`; `Links` takes the colon too but may run its references as a following bulleted list. Nothing else by default.

**The template is enforced at the write path, not by convention alone.** `issue create` and `issue update` validate the title and body before sending the mutation and refuse — non-zero exit, nothing written — anything off-template: a missing canonical header, a link target that isn't an absolute URL, a retired `SPEC.md` or `.pulsar/memories` pointer, or an ordinal/label title prefix. Because this tool is the sole sanctioned write path, a malformed ticket cannot be created *through it*; the one hole the model can't close is a body typed directly into the Linear web UI, which the `lint` sweep catches after the fact. The rules live in `validation.py`, shared by both write verbs and `lint`, so the gate and the audit can never disagree.

**Links are real URLs, never repo-relative paths.** Linear has no repo context, so a bare `core/AGENTS.md` renders as inert monospace text that resolves to nothing — a breadcrumb, not a link. A spec link must be a full GitHub blob URL on `dev` with the complete path (`https://github.com/outernet-foundation/placeframe/blob/dev/packages/python/core/AGENTS.md`), so it stays clickable and tracks the living file.

**Sequence lives in `blocks` relations, never in titles or prose.** The graph is queryable ("what is unblocked right now?") and stays correct when the plan changes; prose ordering is neither.

**A big initiative is a Project + phase-issues + a `blocks` graph + just-in-time file sub-issues.** The project's direct issues are coarse phases. The fine, ~1:1-with-PR units are sub-issues created at the last responsible moment when a phase is picked up — never enumerated up front, because per-file scope goes stale before it is worked.

**Priority is global, not per-team.** Three effective levels: Urgent (1), High (2), and No Priority (0) — the default. Most tickets stay at 0 (normal); Urgent is reserved for deadlines or legal requirements, and High for work that blocks other items. Never set Medium (3) or Low (4); "normal" is the absence of priority, not an explicit level. Set it with `--priority` on `issue create`/`issue update` (0/1/2 = none/urgent/high); it surfaces in `issue get`, `issue list`, and `issue snapshot`.

**`type/bug` vs `type/defect`.** A bug is wrong behavior whose root cause is not yet determined — investigation is active, and the ticket holds the repro, call stack, and hypotheses. A defect is wrong behavior with a determined root cause — the ticket is a thin acceptance-criteria artifact and the prose lives in repo docs. A bug becomes a defect once its root cause is found; the transition is a label swap, not a team move.

**Snapshot before destructive operations.** Before any destructive verb (`project delete`, `label delete`, `comment delete`, `workflow-state archive`), run `linear snapshot` and commit the output to git. This creates a restore point — `projectDelete` cascades archive to every issue in the project, and other destructive verbs can likewise remove data that has no undo. Git history on the snapshot file is the append-only audit trail: the diff between two snapshot commits shows exactly what a destructive operation changed or destroyed.
